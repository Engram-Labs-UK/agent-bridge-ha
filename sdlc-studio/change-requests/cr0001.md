## Summary

The integration currently enforces a single config entry via `async_set_unique_id(DOMAIN)` + `_abort_if_unique_id_configured()`. This means only one Agent Bridge instance can exist in HA, locked to a single bridge agent. The user wants to add the integration multiple times -- once per agent -- so that each agent appears as a separate conversation agent in HA's voice assistant picker. This enables wake-word routing: "Hey Cora" activates the Cora pipeline (female voice), "Hey Spanners" activates the Spanners pipeline (male voice), each backed by a different bridge agent.

## Problem

### Current behaviour

1. User adds Agent Bridge, selects "cora" as the agent
2. User clicks "Add entry" to add a second instance for "spanners"
3. HA shows "Agent Bridge is already configured" (abort)
4. Only one conversation agent exists in the voice assistant picker
5. No way to have different wake words route to different bridge agents

### Why this matters

HA's voice pipeline model assigns one conversation agent per pipeline. Each voice satellite can have its own pipeline. The natural UX for a multi-agent homelab is:

```
Kitchen satellite → "Hey Cora" → Pipeline: Cora → Agent Bridge (cora) → female TTS
Study satellite   → "Hey Spanners" → Pipeline: Spanners → Agent Bridge (spanners) → male TTS
```

This requires two separate conversation agents in HA's picker, which requires two config entries.

### Current HA API limitation context

HA's `async_set_agent()` accepts one agent per config entry. There is no `agent_id` parameter to register multiple agents under a single entry (confirmed on HA 2026.4.1). The correct pattern for per-agent conversation agents is **one config entry per agent**, not one config entry with sub-entities.

## Proposed Changes

### Item 1: Remove unique ID singleton constraint (P1, small)

**Current code** in `config_flow.py`:
```python
await self.async_set_unique_id(DOMAIN)
self._abort_if_unique_id_configured()
```

This prevents multiple entries. Replace with a per-agent unique ID:

```python
agent_id = user_input[CONF_DEFAULT_AGENT]
await self.async_set_unique_id(f"{DOMAIN}_{agent_id}")
self._abort_if_unique_id_configured()
```

This allows multiple entries (one per agent) while still preventing duplicate entries for the same agent.

**Files:** `config_flow.py`

### Item 2: Per-entry device and entity naming (P1, medium)

Currently all entities use generic names:
- `sensor.agent_bridge_bridge_status`
- `binary_sensor.agent_bridge_connected`
- Device name: "Agent Bridge"

With multiple entries, these would collide. Each entry should incorporate the agent name:

| Current | Multi-entry |
|---------|-------------|
| `sensor.agent_bridge_bridge_status` | `sensor.agent_bridge_cora_bridge_status` |
| `binary_sensor.agent_bridge_connected` | `binary_sensor.agent_bridge_cora_connected` |
| Device: "Agent Bridge" | Device: "Agent Bridge - Cora" |
| Conversation agent: "Agent Bridge" | Conversation agent: "Agent Bridge - Cora" |

The config entry title should also reflect the agent: "Agent Bridge - Cora" instead of "Agent Bridge".

**Files:** `sensor.py`, `binary_sensor.py`, `event.py`, `__init__.py`, `config_flow.py`

### Item 3: Shared vs per-entry resources (P1, medium)

With multiple config entries, some resources should be shared (bridge connection) and some should be per-entry (conversation agent, session). Current architecture:

| Resource | Current | Multi-entry approach |
|----------|---------|---------------------|
| Bridge client | Per-entry | **Share if same bridge URL+token**, create new if different bridge |
| Coordinator | Per-entry | **Share if same bridge** -- all entries pointing to the same bridge URL should share one coordinator to avoid redundant polling |
| Session manager | Per-entry | Per-entry (each agent has its own session) |
| Conversation agent | Per-entry (one) | Per-entry (one per agent) -- this is the goal |
| Sensors | Per-entry | Per-entry with agent-qualified names |
| Services | Global (once) | Global (once) -- `send_message` accepts `agent_id` parameter already |
| Webhook | Per-entry | **Share if same bridge** -- one webhook subscription per bridge, not per agent |

**Sharing pattern:** On `async_setup_entry`, check if another entry already has a client+coordinator for the same `bridge_url`. If so, reuse it. Store shared resources in `hass.data[DOMAIN]["shared"][bridge_url]` with a reference count. On unload, decrement the reference count and only clean up when it reaches zero.

**Files:** `__init__.py`, `coordinator.py`, `webhook.py`

### Item 4: Config flow UX for second entry (P1, small)

When the user clicks "Add entry" and enters the same bridge URL+token, step 1 should recognise this is the same bridge and skip straight to agent selection. The agent dropdown should exclude agents already configured in other entries.

```python
# In async_step_agents, filter out already-configured agents
existing_agents = set()
for entry in self.hass.config_entries.async_entries(DOMAIN):
    existing_agents.add(entry.data.get(CONF_DEFAULT_AGENT))

available_agents = {
    a["id"]: f"{a.get('name', a['id'])} ({a.get('status', 'unknown')})"
    for a in self._agents
    if a["id"] not in existing_agents
}
```

This prevents the user from accidentally creating two entries for the same agent.

**Files:** `config_flow.py`

### Item 5: Service routing with multiple entries (P2, small)

The `agent_bridge.send_message` and `agent_bridge.invoke_tool` services currently grab the first config entry's data (`_get_entry_data`). With multiple entries, they should:

1. If `agent_id` is specified: find the entry configured for that agent
2. If `agent_id` is not specified: use the first entry (backwards compatible)

```python
def _get_entry_data(hass: HomeAssistant, agent_id: str | None = None) -> dict:
    entries = hass.data.get(DOMAIN, {})
    if agent_id:
        for entry_data in entries.values():
            coordinator = entry_data.get("coordinator")
            if coordinator and coordinator.data:
                # Find the entry whose configured agent matches
                configured_agent = entry_data.get("configured_agent")
                if configured_agent == agent_id:
                    return entry_data
    # Fall back to first entry
    return next(iter(entries.values()))
```

**Files:** `services.py`

### Item 6: Entry title reflects agent name (P1, trivial)

Set the config entry title to include the agent name so the HA UI shows:

```
Integration entries:
  Agent Bridge - Cora       [⚙️] [⋮]
  Agent Bridge - Spanners   [⚙️] [⋮]
```

```python
# In async_step_agents
agent_name = next(
    (a.get("name", a["id"]) for a in self._agents if a["id"] == agent_id),
    agent_id,
)
return self.async_create_entry(
    title=f"Agent Bridge - {agent_name}",
    data={...},
)
```

**Files:** `config_flow.py`

## End-to-End User Journey

After this change:

1. **Settings > Add Integration > Agent Bridge**
2. Enter bridge URL + token → discovers 12 agents
3. Select "Cora" → creates entry "Agent Bridge - Cora" with conversation agent
4. **Settings > Add Integration > Agent Bridge** (again)
5. Same bridge URL + token → discovers agents, Cora is greyed out (already configured)
6. Select "Spanners" → creates entry "Agent Bridge - Spanners" with second conversation agent
7. **Settings > Voice assistants**
8. Create pipeline "Cora": conversation agent = "Agent Bridge - Cora", wake word = "Hey Cora", TTS = female voice
9. Create pipeline "Spanners": conversation agent = "Agent Bridge - Spanners", wake word = "Hey Spanners", TTS = male voice
10. Assign Kitchen satellite to Cora pipeline, Study satellite to Spanners pipeline
11. "Hey Cora, turn on the lights" → Cora responds (female voice)
12. "Hey Spanners, what's the weather?" → Spanners responds (male voice)

## Out of Scope

- Per-agent TTS voice selection (that's an HA pipeline setting, not an integration concern)
- Wake word training (that's an ESPHome / openWakeWord concern)
- Multiple bridge instances (different URLs) -- this works already since the unique ID is per agent, not per bridge
- Per-agent entity exposure settings (all entries share the same HA expose settings)

## Risks

- **Entity ID migration:** Existing users with a single entry will keep their current entity IDs. New entries get agent-qualified IDs. No migration needed for existing setups, but the first entry's entities won't match the naming pattern of subsequent entries. Acceptable for v0.2.0; a future version could offer migration.
- **Coordinator sharing complexity:** Reference-counting shared coordinators adds state management. If an entry is unloaded mid-poll, the coordinator must handle it gracefully. Mitigate with defensive checks in the coordinator's update callback.
- **Redundant health sensors:** Each entry creates its own bridge status and connectivity sensors. With 5 agents, that's 5 copies of the same bridge health data. Could optimise by only creating health sensors on the first entry, but this adds complexity for marginal benefit. Accept the duplication for v0.2.0.

## Acceptance Criteria

1. User can add Agent Bridge integration multiple times, once per agent
2. Each entry creates a separate conversation agent visible in HA's voice assistant picker
3. Each entry has agent-qualified entity names (no collisions)
4. Config entry title shows agent name ("Agent Bridge - Cora")
5. Second add flow excludes agents already configured
6. Entries sharing the same bridge URL share a single coordinator (no duplicate polling)
7. Services route to the correct entry based on `agent_id`
8. Removing one entry does not affect other entries
9. Existing single-entry setups continue to work without reconfiguration
