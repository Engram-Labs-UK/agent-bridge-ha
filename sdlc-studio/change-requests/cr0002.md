## Summary

The integration is **v0.1.0**, its README still targets **"Agent Bridge v3.1.0+"**, and it was last validated against HA 2026.4.1. The bridge has since reached **v4.36.0** (a major version + ~7 weeks of CRs) and Home Assistant's conversation surface has moved on by ~12 release cycles. The **reactive path is broken for multiple live agents (Cora, Spanners)**: they reply but never actuate.

A multi-agent gap-analysis (2026-06-01, adversarially verified) found **two independent critical root causes — neither a removed endpoint** — plus a tier of request/response shape drift and unadopted v4.36 surfaces. This CR re-platforms the reactive path onto Home Assistant's modern `ConversationEntity` + `ChatLog` + LLM-API model and re-aligns the bridge client to the v4.36 contract.

## Problem

### Root cause 1 — actuation is structurally inert (G1, critical)
The home-control loop cannot function end-to-end:
- HA never advertises a tool schema — `conversation.py` builds `messages=[system,user]` only; `client.chat` has no `tools` param.
- The **v4.36 bridge has no tool_calls contract**: `ChatRequestBody` (chat.ts:141-189) declares no `tools`/`functions` field, the http-openai adapter (http-openai.ts:398) rebuilds the outbound body without it, and the response (chat.ts:889-902) only ever carries `role`/`content`/`finish_reason:'stop'` — never `tool_calls`.
- Therefore `extract_tool_calls` (helpers.py:74-86) always returns `[]` and the loop (conversation.py:262) exits on iteration 1 with free text. **This is why live agents reply but never act.**

**Resolution (Option A):** stop relying on the OpenAI `tool_calls` round-trip; delegate tools + entity context to HA's Assist LLM API via `chat_log.async_provide_llm_data()` and validated `llm.Tool` calls. This removes the cross-repo dependency entirely.

### Root cause 2 — built on Home Assistant's legacy conversation API (G2, critical)
`conversation.py` subclasses `AbstractConversationAgent` and registers via `async_set_agent()`; there is no `conversation` entity platform (`const.py PLATFORMS=['sensor','binary_sensor','event']`). The per-agent path calls `async_set_agent(..., agent_id=...)` — a kwarg HA never accepted (commit `8130825`); its call site was removed, leaving `async_setup_per_agent_conversations` (conversation.py:520) as **uncalled dead code** (US0015 marked Done but inert). This blocks `ChatLog`, the LLM API and multi-agent entities.

**Resolution:** migrate to a `ConversationEntity` per agent via **config subentries** (HA 2025.2+), the pattern the OpenAI/Google conversation integrations use; implement `_async_handle_message(user_input, chat_log)`; adopt `ChatLog` for history + LLM-API plumbing. Supersedes CR-0001.

### Contract & adoption drift (high/medium)
`/v1/tools/invoke` field names (G6), `/v1/broadcast` body+response shape (G5), SSE delta/terminal format + swallow-everything error handling (G7), webhook health payload (G11), dropped voice metadata (G12); unadopted v4.36 surfaces — rich health/circuit/metrics (G8), `x-bridge-mcp-caller`/crew/include= (G9), full webhook catalogue incl. `bridge:upgraded` (G10), `/v1/agent-context` drift-signalling (G13), `/v1/health` tri-state + toolSurface (G14), capability taxonomy gating (G15), HA-version pin/CI (G16). Plus a **fail-open exposure bug** (`exposure.py:125-127` bare-except returns True → exposes all entities).

## Scope (Option A)
1. Re-platform conversation onto a `ConversationEntity` entity platform, one entity per bridge agent via config subentries; add `conversation` to `PLATFORMS` + manifest deps; delete the dead `async_set_agent`/`async_setup_per_agent_conversations` code.
2. Implement `_async_handle_message(user_input, chat_log)`; adopt `ChatLog` for history; retire `SessionManager`-as-history.
3. Restore actuation via HA's Assist LLM API: `chat_log.async_provide_llm_data()` + validated `llm.Tool`; retire `exposure.py`/`tool_executor.py` (retain only as an explicit, logged fallback); fix the fail-open exposure to **fail closed**.
4. Re-align the bridge client to v4.36 shapes: `tools.invoke {agent,tool,args}`; `broadcast {messages:[{role,content}],tags}` (non-empty tags) + responses-object handling; SSE `{text}` + `event:done` (or disable streaming until viable) + stop swallowing errors; webhook `{agentId,healthy}` handling; voice metadata via prompt-fold (or a bridge passthrough — OQ6).
5. Adopt the v4.36 discovery/health surface: send `x-bridge-mcp-caller`; capture the CR-0097 health block + CR-0245 metrics + capability taxonomy; gate entity creation on `capabilityEnvelope`; read `/v1/health` (tri-state + toolSurface); subscribe to the full webhook catalogue; read `/v1/agent-context` to raise an HA repair issue on version/deprecation drift.
6. Pin + CI-test against a current HA core; correct README (v4.36 floor) + TRD (drop the phantom `/health?depth=deep`).

## Out of scope
Per-agent TTS voice selection / wake-word training; any `agent-bridge` feature beyond what Option A needs (none for actuation — the optional voice-metadata passthrough, OQ6, would be a separate `agent-bridge` CR if chosen); changing HA's exposed-entities model; forced entity-ID migration of existing installs (offer, don't force); altering the proactive `/api/mcp` path (DBee) — this CR documents the boundary, not the path.

## Risks
- HA conversation/LLM API is itself a moving target — needs a CI matrix against current HA (G16).
- Heterogeneous live agents (Cora/Spanners run their own harness/system prompt) may not consume HA's `llm.Tool` surface without per-agent wiring — **live-agent consult mandatory** before freezing US0027.
- Config-subentry migration may cause entity-ID churn for existing single-entry installs — offer migration, don't force.
- Failing exposure closed could hide entities on older HA where the import genuinely fails — use a deliberate, logged fallback.
- `x-bridge-mcp-caller` introduces a caller identity the bridge authorises by crew — a wrong caller could over/under-expose agents.
