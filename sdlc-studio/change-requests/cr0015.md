# CR-0015: URL-encode path parameters in the bridge client

> **Status:** Implemented
> **Priority:** P3
> **Type:** design-change
> **Requester:** Code + security review (RV-requested, 2026-07-04)
> **Date:** 2026-07-04
> **Affects:** client
> **Depends on:** —
> **GitHub Issue:** —

## Summary

`BridgeClient.agent_usage`, `memory_record` and `memory_recall` interpolate `agent_id` into the request path unencoded (`f"/v1/agents/{agent_id}/usage"` etc.). An `agent_id` containing `/`, `?`, or `#` rewrites the request target — e.g. `../../doctor` walks the path to a different endpoint. Exploitation requires a hostile or misconfigured input (service-supplied ids are roster-validated; usage polling uses bridge-supplied ids; the memory services' default-agent fallback comes from `entry.data`), so this is hardening rather than an live vulnerability — but the client is the trust boundary and should be safe by construction, matching how `memory_recall` already quotes its `?q=` value.

## Problem

Path construction trusts callers to pass a URL-safe id; nothing enforces it, and the id ultimately originates from bridge discovery (an external system).

---

## Proposed Changes

### Item 1: Quote all path-interpolated identifiers

**Priority:** P3 · **Effort:** XS

`from urllib.parse import quote` at module level (drop the function-local import in `memory_recall`); use `quote(agent_id, safe="")` in `agent_usage`, `memory_record`, `memory_recall`, and `unregister_webhook` (`subscription_id`).
