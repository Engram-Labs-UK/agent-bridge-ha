# CR-0014: Harden the inbound webhook (local-only, POST-only, validated payloads, persistent id)

> **Status:** Proposed
> **Priority:** P2
> **Type:** design-change
> **Requester:** Code + security review (RV-requested, 2026-07-04)
> **Date:** 2026-07-04
> **Affects:** webhook, coordinator, __init__, const
> **Depends on:** BG0014
> **GitHub Issue:** —

## Summary

The bridge webhook endpoint is registered with HA defaults: reachable from anywhere HA is reachable, accepts POST **and** PUT, applies no payload validation beyond "is JSON", and mints a fresh webhook id every setup. HA webhooks are unauthenticated by design (the id is the secret), so the id **is** the credential — yet it is logged at INFO and never persisted. Anyone who learns the id can spoof `bridge_status` (arbitrary string straight into the sensor state via `async_push_webhook_data`), flip per-agent `healthy` flags, force refresh storms, and fire `EVENT_BRIDGE_UPGRADED` at will (which triggers an authenticated drift-check fetch). The bridge is on the local network and `get_url(..., allow_internal=True, allow_external=False)` already assumes that, so there is no reason for the endpoint to be internet-reachable or method-loose.

## Problem

Defence-in-depth is absent on the one unauthenticated inbound surface this integration owns. Individually each gap is small; together they make webhook-id disclosure (log share, HTTP capture on the LAN) a home-state-spoofing primitive.

---

## Proposed Changes

### Item 1: Register local-only and POST-only

**Priority:** P2 · **Effort:** S

`webhook.async_register(..., local_only=True, allowed_methods=[METH_POST])`. The bridge posts from the LAN; external and PUT access have no use case.

### Item 2: Validate pushed values before they enter coordinator data

**Priority:** P2 · **Effort:** S

- `async_push_webhook_data`: accept a `status` push only when it is a known state (the `_TRISTATE_MAP` outputs / shallow-health vocabulary); ignore and debug-log anything else.
- Require `healthy` to be a bool and `agentId` a string before applying a per-agent push.
- (The non-object-JSON crash is tracked separately as BG0014.)

### Item 3: Persist the webhook id in the config entry

**Priority:** P3 · **Effort:** S

Store the generated id under `CONF_WEBHOOK_ID` in `entry.data` on first setup and reuse it thereafter (standard HA pattern). Today every restart mints a new id and registers a new bridge subscription; an unclean shutdown (crash, power loss) leaks the old subscription on the bridge, which then POSTs to a dead endpoint indefinitely. A stable id also makes Item 1's threat model auditable.

### Item 4: Stop logging the webhook id at INFO

**Priority:** P3 · **Effort:** XS

`_LOGGER.info("Registered HA webhook: %s", webhook_id)` puts the capability secret in the default log level (and in shared diagnostics/log pastes). Drop to DEBUG or log a truncated form.

---

## Impact Assessment

### Existing Functionality

No behaviour change for a legitimately configured bridge on the LAN. A bridge posting via an external URL (unsupported today anyway — registration uses the internal URL) would stop working; that combination is not a supported topology.

### Affected Modules

| Module | Impact | Change Type |
| --- | --- | --- |
| `webhook.py` | register flags, id logging | Modified |
| `coordinator.py` | push-value validation | Modified |
| `__init__.py` / `const.py` | persist + reuse `CONF_WEBHOOK_ID` | Modified |

### Breaking Changes

None expected. Existing installs pick up a persisted id on first restart after upgrade (the bridge subscription is re-registered as it is on every restart today).

---

## Acceptance Criteria

- [ ] Webhook is registered `local_only=True`, `allowed_methods=[POST]`; a PUT and a non-local request are rejected
- [ ] A `status` push with an unknown value does not change `bridge_status`; a non-bool `healthy` push is ignored
- [ ] The webhook id survives an HA restart (persisted in `entry.data`) and only one live bridge subscription exists after repeated restarts
- [ ] The full webhook id no longer appears at INFO level
- [ ] `ruff` + `pytest` green; regression tests cover each gate

## Risks

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| A proxied/NAT'd bridge appears non-local and gets blocked | Low | Medium | Documented; option to relax could be added if a real topology needs it |
| Persisted id conflicts with an existing HA webhook after restore | Low | Low | Fall back to regenerating when registration fails |
