# Change Request CR-0004: Reactive continuity + proactive + multimodal conversation expansion

**Requested by:** Darren Benson
**Date:** 2026-06-05
**Priority:** P2
**Status:** Proposed
**Affects:** conversation, client, exposure, services, webhook, new ai_task platform, const, manifest; co-requisite agent-bridge PR (Telegram outbound image)
**Depends on:** EP0007 (reactive path on ConversationEntity + ChatLog), 0.4.0 caller_context
**Type:** feature-request

---

## Summary

With the reactive path re-platformed (EP0007) and caller-context grounding shipped (0.4.0), the
integration is a solid thin adapter but uses **almost none** of the richer capabilities the
bridge REST surface already exposes, and lags the HA LLM ecosystem on vision, proactive speech
and AI Task. This CR expands conversation capability across six phases, shaped by a competitive
survey, HA developer-docs (Context7), and two live consults with the Cora bridge agent.

## Transport decision (resolved)

**Stay on REST; adopt its unused capabilities. Do not pursue ACP.** Investigation (Phase 0
spike) found the bridge exposes **no inbound ACP server** (ACP is outbound-only, bridge → backend
CLI agents), while REST `/v1/chat/completions` already supports session continuity (channel →
session_id, 24h TTL), SSE streaming, cancellation, progress and image attachments, plus
`/v1/messages` callbacks, `/v1/broadcast` and `/v1/webhooks` for proactive push. ACP would invert
the architecture for little gain (Cora concurred).

## Problem

- **Cold-start each turn.** HA sends `channel=conversation_id` (ephemeral) and discards the
  returned `session_id`, so the bridge's per-channel session is abandoned between commands.
  Multi-turn tasks and confirm-before-actuate break. (Cora's #1 pain.)
- **No vision.** Agents cannot see camera snapshots ("is that a person at the door?"). Safety gap.
- **No proactive speech.** Agents can only respond, never push ("washing machine finished").
- **Dormant streaming.** `chat_stream`/`_stream_chat` exist but the live handler is non-streaming.
- **No AI Task / no agent→Telegram image** (the bridge Telegram client has no `sendPhoto`).
- **Thin grounding.** No recent-state-changes, presence ("who's home") or alarms/calendar context.

## Scope (six phases → EP0008)

0. **Spike (done):** confirm the bridge persists session by channel (24h TTL). Outcome: fix the
   channel *key*, don't build a session store.
1. Session continuity via a stable, idle-windowed channel key (default 10 min).
1b. Response streaming to TTS (only within existing SSE).
1c. Richer grounding envelope: recent state changes, presence, upcoming alarms/calendar.
2. Camera/vision input (camera snapshots as image attachments).
3. Confirm-before-actuate (pendingAction + timeouts + severity), riding on session continuity.
4. Proactive announcements (HA-as-client listener + `assist_satellite.announce`; needs an
   agent→HA trigger convention).
5. Agent→Telegram camera snapshot (HA snapshot-send + co-requisite bridge `sendPhoto` PR).
6. AI Task platform (tightly scoped: `generate_data` with structure; defer image/registry).

## Out of scope

- ACP transport (rejected above). HA `llm.Tool` structured tools (contradicts Option A; agent
  self-actuation via `/api/mcp` stays the model). AI Task schema registry / approval workflows.

## Acceptance

Each phase ships as a minor release with unit tests (CI-gated; local suites can't fully run —
HA needs Python 3.13), a reconcile pass and a full code review. Live validation on 10.0.0.209 +
`mcp__bridge` tools + the conversation journal where applicable.
